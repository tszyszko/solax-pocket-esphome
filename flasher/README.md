# In-app factory flasher (ESP-IDF 4.4.4)

> **Status: built, NOT YET EXERCISED ON HARDWARE.** Its building blocks are
> proven separately (an IDF 4.4.4 app delivered by SolaX's MQTT OTA boots and
> reaches the network; an ESPHome factory.bin written by esptool at 0x0
> runs), but the flasher's own write path has never run on a dongle. Have a
> serial rig ready before you push it.

The stock bootloader is ESP-IDF 4.x: it boots a pushed IDF 4.4 app but refuses
IDF 5.x images such as ESPHome's, and SolaX's OTA only ever writes an app slot.
So the flasher is a small IDF 4.4 app that, once delivered through SolaX's OTA,
rewrites the whole layout from ESPHome's `factory.bin` (bootloader, partition
table, app) the way `esptool write-flash 0x0 factory.bin` would.

## Sequence

1. Join Wi-Fi (RAM-only config, no NVS writes), `POST /hello` with the physical
   address it runs from.
2. Back up the full 4 MB: 16 × `POST /dump/<offset>` of 256 KB each (up to 4 attempts
   per piece; any failure halts before anything is written).
   `tools/ota_server.py` reassembles them into `stock-backup.bin` and prints the MD5,
   and also writes `stock-backup-restorable.bin` (see [Backup and restore](#backup-and-restore)).
3. Stream `GET /factory.bin` and check length and MD5 against `EXP_LEN` /
   `EXP_MD5` (compiled in from `main/factory_expect.h`, generated by `build.sh`).
4. `POST /ready`, then poll `GET /go` every 5 s until the body is `GO`.
   Nothing is written to flash before this point.
5. Download `factory.bin` 0x0..0x10000 (bootloader, partition table,
   otadata/phy) into a 64 KB RAM buffer (allocated at boot) and check it
   against `EXP_HEAD_MD5`. Any failure halts **before anything is written**.
6. Write, each 4 KB sector erased, written and read back:
   1. the **app** (`factory.bin` 0x10000..end) to the target slot, streamed
      over HTTP (the last network-dependent write),
   2. the **partition table** (0x8000..0x9000), from RAM,
   3. **otadata + phy** (0x9000..0x10000): erased (app0 case) or crafted (app1 case), from RAM,
   4. the **bootloader** (0x0..0x8000) **last**, from RAM, which takes under a second.

   Every `Range` download (the head and the app) must come back `206` with a
   `Content-Length` equal to the requested size, otherwise the flasher halts
   (`RANGE_BAD`): a server that ignores `Range` would otherwise hand it the
   file from offset 0.
7. MD5 the written flash (app read from where it was put, 0x9000..0x10000
   counted as 0xFF as in the file) and compare with `EXP_MD5`; `POST /done` and
   reboot only on a match. Any failure: `POST /HALT` with the reason, repeated
   every 30 s, no reboot.

## Slot logic

SolaX's OTA writes the pushed app into whichever stock slot is not running:

| Flasher runs from | ESPHome app goes to | otadata |
|---|---|---|
| stock `ota_1` (0x110000), the usual case when stock runs from `ota_0` | ESPHome `app0` (0x10000) | 0x9000..0x10000 erased → bootloader picks app0 |
| stock `ota_0` (0x10000) | ESPHome `app1` (0x1D0000), so the flasher never overwrites itself | crafted at 0x9000: `ota_seq` = 2, CRC32 of the seq at +28, second copy erased → app1 |
| anything else | nothing | halts with `UNKNOWN_SLOT` |

This relies on ESPHome's default ESP-IDF 4 MB layout (otadata 0x9000, phy
0xB000, app0 0x10000, app1 0x1D0000, both 0x1C0000; nvs 0x390000) and on the
factory image ending before 0x110000. `tools/check_factory.py` enforces both
before the flasher is built.

## Failure windows

* Before GO: nothing written. The flasher is still sticky, though: every boot
  re-runs backup → verify → wait. Re-run `convert.py --resume`, or restore by serial.
* After GO, before the app write: the 64 KB head download and its MD5 check.
  A failure here halts with nothing written.
* During the app write (step 6.1): a network or flash error halts with the
  ESPHome app partly written into the target slot, but the bootloader,
  partition table and otadata are still stock. In the `ota_1` case that slot
  is stock `ota_0`, which is now damaged: serial recovery. In the `ota_0` case
  it is app1 = the tail of stock `ota_1` and `cfg_data`: stock otadata still
  boots the flasher, which starts over.
* Between the partition table and the end of the bootloader (step 6.2–6.4):
  stock IDF 4.x bootloader + ESPHome partition table. These are ~16 sector
  writes from the RAM copy (about a second, no network involved); only a
  power loss, reset or flash error can interrupt them.
  When the flasher runs from stock `ota_1` (ESPHome → app0) a reset in this
  window is very likely unbootable (app0 = IDF 5.x is refused, app1 at
  0x1D0000 is the middle of the flasher image): serial recovery. When it runs
  from `ota_0` (ESPHome → app1), the old bootloader should fall back to app0 =
  the flasher, which starts over. Do not touch the dongle until `done`.
* The writes are destructive for stock: in the `ota_1` case the ESPHome app
  overwrites the stock app in `ota_0`; in the `ota_0` case it is written from
  0x1D0000 on, over the tail of the stock app in `ota_1` **and over `cfg_data`
  (0x210000, the dongle serial) / the start of `offline_data`**. ESPHome
  formats its NVS at 0x390000 on first boot. Only the 4 MB backup puts stock back.
* The backup is taken while the flasher runs, so `stock-backup.bin` is **not a
  pure stock image**: see [Backup and restore](#backup-and-restore).

## Backup and restore

`stock-backup.bin` is the 4 MB flash exactly as the flasher read it: stock
bootloader, partition table, NVS, `cfg_data` (serial) and `offline_data`, the
stock app in one OTA slot, **the flasher in the other**, and stock `otadata`
(0xD000) selecting the flasher. Written back as is, it boots the flasher again.

`tools/ota_server.py` therefore also writes `stock-backup-restorable.bin`: the
same image with otadata rewritten to boot the stock slot (sector 0xD000 = one
valid entry, `ota_seq` 1 → `ota_0` if the flasher ran from `ota_1`, `ota_seq` 2
→ `ota_1` if it ran from `ota_0`; sector 0xE000 erased). The flasher's slot is
taken from its `hello`/`ready` posts (`phys=`/`slot=`), else detected from the
image (the slot whose app descriptor says `solax_flasher`); the `restorable`
log line says which. For an existing backup, or if the server could not tell:

```sh
python3 -I tools/make_restorable.py stock-backup.bin [--flasher-slot ota_0|ota_1]
```

Restore stock by serial: `esptool ... write-flash 0x0 stock-backup-restorable.bin`.
The otadata CRC matches entries read from a real dongle
(`make_restorable.py --selftest`), but a restore of a path-A backup has **not
been tested on hardware**.

## Build

```sh
SSID=... PSK=... REPORT_URL=http://<this-host>:8080 flasher/build.sh build/factory.bin build/flasher.ota.bin
```

`build.sh` validates `factory.bin`, generates `main/factory_expect.h` and
`main/secrets.h` (git-ignored, mode 600), runs `idf.py build` in
`espressif/idf:v4.4.4`, appends the SolaX whole-image CRC-16 trailer and writes
`flasher.ota.bin.json` for `convert.py`. The output contains your Wi-Fi PSK in
clear text.

`sdkconfig.defaults` notes: `CONFIG_SPI_FLASH_DANGEROUS_WRITE_ALLOWED=y` is what
allows writing the bootloader and partition-table regions; Wi-Fi NVS and PHY
calibration storage are off so the flasher writes nothing it does not mean to.
